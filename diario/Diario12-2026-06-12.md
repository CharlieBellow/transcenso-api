1. EVOLUÇÃO ARQUITETURAL: DA EXPLOSÃO DE ARQUIVOS À COESÃO
----------------------------------------------------------------------
Nesta etapa, finalizei a implementação de todos os Controllers e Casos 
de Uso (UseCases) para os três domínios principais do sistema. 

A grande virada de chave foi a consolidação do padrão de rotas por 
especificidade no NestJS para evitar conflito de "curingas" (HTTP 404/500). 
Para que arquivos isolados pudessem coexistir sem confundir o roteador, 
adotei prefixos explícitos nas rotas de busca GET:
- /people/id/:id       -> Busca por ID único (formato UUID)
- /people/cpf/:cpf     -> Busca por CPF (regra específica de Person)
- /genders/slug/:slug   -> URLs amigáveis para o Front-end

Também padronizei os endpoints do recurso de Pessoa para o plural 'people',
garantindo consistência semântica em toda a API Rest.

2. CONCEITO CHAVE: INJEÇÃO DE DEPENDÊNCIA (DI) EM POO
----------------------------------------------------------------------
Compreendi o papel crucial do padrão Injection Dependency (Injeção de 
Dependência) na Programação Orientada a Objetos. 

- O Problema: Sem DI, uma classe fabrica suas próprias dependências de forma 
  rígida (acoplamento forte). Se a dependência muda, a classe quebra.
- A Solução: Inversão de Controle. A classe declara o que precisa no seu 
  'constructor' através de uma interface abstrata e o framework (NestJS) 
  fornece a instância real de fora para dentro na inicialização.

Aplicações Práticas no TransCenso:
O 'FindByCpfPersonUseCase' não sabe como o banco de dados funciona. Ele 
apenas pede os contratos (PersonRepository, GenderRepository, etc.) no 
seu construtor. Isso traz dois benefícios brutais para a arquitetura:
1. Desacoplamento: Posso trocar o Prisma por qualquer outro ORM no futuro 
   sem alterar uma única linha de regra de negócio dos Casos de Uso.
2. Testabilidade: Permite injetar repositórios falsos em memória para rodar 
   testes unitários ultra velozes, simulando o banco sem tocá-lo.

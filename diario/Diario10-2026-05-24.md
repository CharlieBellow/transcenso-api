# Garantia de Runtime Context (Injeção Manual via Dotenv):
"Descobri que a CLI do Prisma isola o contexto de execução de forma tão estrita que o process.env não absorve o arquivo .env local automaticamente. Apliquei uma boa prática de infraestrutura importando e executando o dotenv.config() explicitamente no topo do prisma.config.js. Isso blinda o arquivo de configuração, garantindo que a URL de conexão esteja sempre disponível no runtime da CLI."


# Substituição de Herança por Composição no Prisma 7 (Infra Pattern):
"Identifiquei que a herança direta de PrismaClient engessava a inicialização do container de Inversão de Controle (IoC) do NestJS devido às validações rígidas do construtor da versão 7. Refatorei o PrismaService adotando o princípio de design de Composição, instanciando o PrismaClient internamente de forma isolada. Adicionei o prisma.config.js no escopo do tsconfig.json para normalizar o parsing do analisador estático (ESLint) na raiz do projeto."


# Adequação Arquitetural ao Prisma 7 (Driver Adapters & Custom Output):
"Através da análise da documentação oficial do Prisma 7, identifiquei duas mudanças drásticas de paradigma: a necessidade de desacoplar o cliente do node_modules gerando-o localmente em src/generated/prisma, e a obrigatoriedade de usar o padrão Driver Adapter (@prisma/adapter-pg) acoplado a um Pool de conexões do driver pg nativo. Implementar essa estrutura eliminou os erros de tipagem estrita no construtor do PrismaClient e alinhou a camada de infraestrutura com as especificações modernas do ecossistema."

# 🚨 O Problema: Incompatibilidade de Build e Runtime
O projeto quebrou após a migração para o Prisma 7. Dois fatores causaram o travamento total do sistema:

Conflito de Módulos (ESM vs. CJS): O Prisma 7 gera arquivos em ES Modules (.js nativo) por padrão, enquanto o ecossistema padrão do NestJS opera estritamente em CommonJS (require).

Arquivos Fantasmas no Build (dist/): O compilador do NestJS ignorava a pasta customizada src/generated/prisma durante o processo de build, gerando o erro de runtime MODULE_NOT_FOUND.

🛠️ A Solução Aplicada (A Estratégia)
Forçar CommonJS no Schema: Adicionada a diretiva moduleFormat = "cjs" dentro do bloco generator client no arquivo schema.prisma. Isso forçou o Prisma a gerar um cliente legível pelo NestJS.

Ajuste de Caminhos Relativos com Extensão: Os imports do PrismaService e dos mappers foram alterados de caminhos absolutos (src/...) para caminhos relativos explícitos e adicionado o sufixo .js (ex: ../../../generated/prisma/client.js) para guiar o Node.js corretamente dentro da pasta de produção.

Mapeamento de Ativos no Nest (nest-cli.json): Como o projeto não possuía o arquivo, foi criado o nest-cli.json na raiz, configurando a propriedade compilerOptions.assets para incluir generated//*. Isso obriga o NestJS a copiar fisicamente a pasta de tipos e binários do Prisma para dentro de dist/ a cada build incremental.

💡 Lição Aprendida para o TransCenso-API: > Em arquiteturas DDD complexas, a camada de infraestrutura exige atenção minuciosa na fronteira entre o compilador do TypeScript e o runtime do Node.js. Garantir que as ferramentas falem o mesmo formato de módulo (cjs) e mapear arquivos gerados automaticamente como recursos estáticos (assets) evita falsos positivos e garante a integridade do deployment.
